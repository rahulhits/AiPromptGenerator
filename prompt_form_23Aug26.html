1 Ticket / Branch Context

Always include the ticket, branch, and code-change rule. The marker is what keeps the diff reviewable.

Code change rule (paste verbatim into the prompt) 
Every change must be wrapped with:

  //<TICKET> - Rahul - <DD MMM YYYY> start
  // <one-line note explaining the WHY of the change>
  // <commented-out old code>
  <new implementation>
  //<TICKET> - Rahul - <DD MMM YYYY> end

Never delete existing code — comment it out and add new code between the markers.

2 Environment

Pre-filled with the project stack so the AI never has to guess the runtime. Edit only if this issue involves something different.

3 Symptom (literal)

Be a camera — capture what's actually on screen. "Shows literal {{defaultdate}}" beats "date is broken".

One ticket can affect multiple fields — list each one separately.

Add as many as you need — broken, working, expected, mobile, etc. The label appears in the generated prompt.

4 Expected Behaviour & Definition of Done

One sentence. Concrete. The "should" sentence the test would check. Then list checkable done-criteria — the AI must verify each before reporting done.

5 Files Involved

Start with the module folder so the AI knows where to focus. Then list the specific files you already know about.

Optional. If set, the AI searches this folder first before scanning other modules.

Path is auto-built from the module folder above. Edit manually if needed.

6 Already Tried / Ruled Out

The #1 cause of multi-shot loops is the AI retrying things you already disproved. List each attempt and its result.

7 Constraints / Do-Not-Touch

Limit the blast radius. Prevents the over-eager wide refactor that breaks other modules.

8 Standing Rules

Tick each rule that applies to this issue. The verbatim text is included automatically.

9 The Ask

Tick what you want the AI to do. The "root cause" item is the most important one.
